RepoSpector help

RepoSpector reviews GitHub pull requests and GitLab merge requests with the AI model you choose, using your own key. It runs in your browser; there is no RepoSpector server.

Get started

Settings opens by itself after you install RepoSpector. Its Get started list shows what is left. To open settings later, right-click the toolbar icon, then Options.

  1. AI provider and your API key. RepoSpector uses your own key (bring your own key): you pay the provider directly, and the key is sent only to them. Pick Anthropic, OpenAI, Google Gemini, or Ollama to run on your own computer. Paste your API key. The first time, also choose a passphrase that encrypts your keys on this device (you enter it once per browser session), or tick the box to keep keys in memory only until Chrome closes. Press Check and save key: RepoSpector asks the provider which models the key can use (free, no tokens spent). If the provider rejects the key, you see why and nothing is saved. If it works, the key is saved and the model list shows only the models that key can use, recommended ones (with prices) first; the first time, the recommended model is chosen for you. To change it, pick another and press Save model. Check again re-checks a saved key and refreshes the list; the list is also refreshed daily. For Ollama, press Check connection and load models.
  2. GitHub and GitLab. Choose GitHub or GitLab. The address is filled in (github.com or gitlab.com); change it for GitHub Enterprise or self-managed GitLab. Paste a personal access token if you review private repositories or want to post drafts (the page links to the host's token page with the right scopes filled in), then press Check and connect. Chrome asks you to allow that site. The token is checked first by reading your own profile: if the host rejects it, you see why and nothing is saved; if it works, you see the account it signs in as and whether it can post drafts. Connected hosts have Check token, Replace token (or Add token) and Disconnect.
  3. Open a pull request, click the RepoSpector icon to open the side panel, check the estimated cost, and press Review this pull request. You can close the panel; the review keeps running. The side panel is hidden while the settings tab is in front.

Key security in settings locks your keys or deletes them all.

How a review works

  1. Read the pull request: its title and diff, from GitHub or GitLab.
  2. Read the repository: RepoSpector downloads the repository at the pull request's commit, indexes it on your device, and finds where the functions, methods and classes the change calls, constructs or extends are defined. It then fetches only those files. The index is saved, so the next review of the same repository reads only what changed. On github.com, Chrome asks once for permission to download from codeload.github.com.
  3. Review twice: once with the diff alone (the review we measured), and once with that code from other files, to catch wrong arguments, ignored return values, missing error handling and similar mistakes in how the change uses existing code. The two results are merged; a finding only the second review made says "Found by the pass that read code from other files".
  4. Check each finding with a second pass that labels and ranks it, and rates its impact.
  5. Apply your team's feedback.

If the repository cannot be read (larger than 300 MB, private without an access token, permission declined, or languages RepoSpector does not index), the review still runs on the diff and says why. Reading code from other files makes a review cost up to about twice as much; the estimate before you start includes it. Supported languages for this: Python, Go, Java, Ruby, JavaScript and TypeScript.

Reading a review

Each finding shows its file and line, what goes wrong, and a label from a second check:

Verified
A second pass tried to disprove the finding and could not.
Suspected
The second pass found evidence against it, or your team marked similar findings as not useful. The reason is shown. Suspected findings are kept, listed last, because some are still real.
Not checked
The second pass's answer could not be read.

The second check also tags each finding with how much it would matter if real:

High impact
A security hole, data loss or corruption, a crash, or a main feature broken for most users.
Medium impact
Wrong behaviour for some cases or inputs, or a failure with a workaround.
Low impact
A rare edge case, a minor or cosmetic effect, or maintainability only.

Impact is the model's judgement, not measured. A finding without a tag was not rated (for example when the second check's answer could not be read).

Findings are ordered by how likely they are to be real defects, not by impact. On our test set, the first finding was a real bug about 70% of the time, so reading from the top pays off.

Posting drafts

Tick the findings you want and press Post … as a draft review. On GitHub this creates a pending review, on GitLab draft notes. Only you can see them until you submit or publish them on the site, so you can edit or delete any of them first.

  • RepoSpector will not post if the pull request has new commits since the review, because the lines would be off. Review again first.
  • Findings already on the pull request are not posted twice.
  • Tokens need write access to pull requests: on GitHub a classic token with repo, or a fine-grained token with Pull requests: Read and write; on GitLab the api scope. Test token in settings tells you whether yours can post.

Feedback

Mark findings Useful, Not useful or Not relevant here, with an optional reason. In later reviews, a finding you marked not useful, or one similar to three or more you marked not useful, is labelled suspected and moved down. Nothing is hidden.

Similar means sharing most of their words. In settings you can turn on meaning-based matching, which also catches the same point worded differently. It downloads a small model (22 MB) once from Hugging Face and runs on your device. It is approximate: in our tests it caught most reworded comments, and occasionally matched a different problem in the same area. Matches only lower a finding; they never hide it.

Feedback stays on your device. To share it with your team, use Export as JSONL in settings and commit the file as .RepoSpector/feedback.jsonl.

Where code is used

After a review, Show where this code is used uses the repository index (already built during the review, so usually instant). Each finding then shows the function or class it is in, who calls it, and its subclasses, with links to the exact lines. Nothing is sent to the model.

  • The index is saved on your device. The same commit opens instantly next time; after a new push only changed files are read again.
  • Callers are matched by name, so a list can include unrelated code that happens to share the name.
  • Supported languages: Python, Go, Java, Ruby, JavaScript, TypeScript.
  • Repositories over 300 MB (compressed) are not downloaded.

On pull request pages, findings are also marked beside their lines with a small RS badge (teal: verified, grey: other). Hover it to read the finding.

Cost

Before each review the panel shows an estimated cost range, from the size of the change and the model's published price (the date of the prices is shown). After the review it shows what was actually used. You pay your provider directly. Ollama has no model cost.

Fixing problems

"Your keys are locked"
Open settings and enter your passphrase. Keys stay unlocked until Chrome closes.
"Could not read this pull request (404)"
The repository is private or the token cannot see it. Add or replace the access token for that host in settings.
Ollama: the review fails to reach the model
Ollama refuses browser extensions unless you allow them. Set the environment variable OLLAMA_ORIGINS to chrome-extension://* and restart Ollama.
"You already have a pending review on this pull request"
GitHub allows one pending review per person. Submit or discard it on GitHub, then post again.
"The pull request has new commits since this review"
Press Review again, then post.
"This review stopped…"
Chrome closed the background page that runs reviews. Press Resume review; finished steps are not paid for again.
No RS markers on the page
Open the Files changed tab (Changes on GitLab) and expand collapsed files. GitLab markers depend on GitLab's page layout and may not appear on every version.
