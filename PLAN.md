# Build plan

Follows the release plan in `RepoSpector.md`. Measure first, then build the reviewer.

## What we learned from the previous codebase (deleted, archived in Trash)

- Its shipped pipeline scored 22.3% F1 on Martian's 50 PRs, last of 8. Recall was the larger gap.
- Graph "advisories" (untested blast radius, high-risk symbol) were 0 of 116 true positives. Don't post graph signals as findings; use the graph only as context.
- An agentic rewrite did not beat the simple pipeline. Add stages only when the eval shows a gain.

## Slice 1 — Foundation (this session)

Goal: anyone can score a reviewer from the repo, and the core rules the doc depends on exist and are tested.

| Package | Contents | Done when |
| --- | --- | --- |
| `packages/core` | Finding and verdict schemas (zod), fingerprint, unified-diff parser, evidence check, judge (dedupe + threshold), risk tier, run state machine that enforces review → verify → finalize | Unit tests pass; no I/O, so it runs in Node and the browser |
| `packages/eval` | Golden-case schema, line-based matcher, precision/recall/F1, CLI `score` | Scores fixture findings against fixture cases, deterministic |
| `packages/mcp` | Local MCP server (stdio): `plan_review`, `get_agent_prompt`, `submit_findings`, `verify_batch`, `finalize`, `get_run_state` | e2e test drives a real git repo through the full flow; out-of-order calls are refused |

Rules carried from the doc:
- A finding whose evidence lines don't exist is rejected at submit.
- `finalize` refuses unless every finding has a verdict, and every verdict cites code that exists.
- Confidence is shown as "uncalibrated" until golden-set tables exist. No made-up precision numbers.
- The server never calls a model and needs no key.
- File reads stay inside the repo root; git runs through `execFile` with validated refs.

What the server cannot prove: that the verifier ran in a fresh subagent. It can enforce order and completeness only. The docs say so.

## Slice 2 — Measure (in progress)

Golden set: Martian's offline benchmark (50 PRs, 173 golden comments, MIT), vendored in `eval/data/martian`. Judge: Martian's prompt verbatim, Sonnet 4.5 (one of their three judges) through `claude -p`.
Split: the 13 "pilot" PRs (first 2 per repo) are for tuning; the other 37 are held out and must not be used to tune prompts.

## Slice 4 — Chrome extension (in progress; full spec across sessions, user decision 2026-11-21)

Pipeline: the measured best (single review pass → verifier that labels → feedback filter), not specialists. Order: C1 foundation · C2 key vault · C3 git hosts in the browser (shared request logic in core) · C4 providers + presets · C5 offscreen pipeline with resume and cost estimate · C6 side panel UI, posting drafts, feedback, diff markers · C7 OAuth (needs registered OAuth apps from the user) · C8 repo-archive graph in a worker (needs an unzip dependency: approval) · C9 native-messaging local mode, embedding filter.
